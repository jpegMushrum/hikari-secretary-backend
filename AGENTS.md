# Backend

В составе платформы применяй также корневой `AGENTS.md`.

## Реализация

- Go backend — единственный владелец бизнес-данных и правил. Bot API
  и Admin API вызывают общие сервисы, а не дублируют бизнес-логику.
- Сохраняй авторизацию административных endpoints и отдельный сервисный
  токен Bot API. Не переноси dev-авторизацию в production.
- Связанные изменения данных, аудит и постановку уведомлений в outbox
  выполняй атомарно. Учитывай повторную обработку фоновых задач.
- Новые изменения схемы оформляй новыми миграциями; не переписывай уже
  выпущенные миграции. SQLite используется только как источник импорта.
- Форматируй изменённые Go-файлы через `gofmt`.

## Проверки

- Из этого каталога: `go test ./...`.
- Для SQL, миграций, репозиториев и импорта дополнительно:
  `go test -count=1 -tags=integration ./...` с `TEST_DATABASE_URL`,
  указывающим на выделенную тестовую PostgreSQL, не production.
- При изменении мигратора проверяй применение на пустой схеме и повторный
  запуск. Для импорта проверяй повторный запуск и сохранность источника.
- Для API проверяй права, валидацию, ошибки, пагинацию и изменённое поведение.
  Не заменяй SQL-проверки исключительно моками.
- Если PostgreSQL недоступен, явно сообщи о непройденной проверке.

## Документация и делегирование

- Синхронизируй `openapi/openapi.yaml`, `docs/admin-api.md`, примеры env
  и CHANGELOG с изменёнными контрактами и настройками.
- Для существенных изменений поручи субагентам ревью diff и сверку документации
  после реализации; раздели файлы между исполнителями.
- Для документации используй `gpt-6.2-sol` с уровнем `low`.
- Для обычного ревью используй `gpt-6.2-sol` с уровнем `medium`.
- Только для сложного ревью миграций, авторизации или очередей используй `gpt-6.2-astra` с уровнем `medium`.
- Если выбранная модель недоступна, сообщи об этом и выполни задачу главным агентом. Другую модель используй только по указанию пользователя.
- Не объявляй невыпущенные изменения релизом.
