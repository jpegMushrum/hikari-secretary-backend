# Hikari Secretary Backend

![Версия](https://img.shields.io/badge/version-v0.3.0--dev-6A5ACD)
![Go](https://img.shields.io/badge/Go-1.27-00ADD8?logo=go&logoColor=white)
![PostgreSQL](https://img.shields.io/badge/PostgreSQL-18-4169E1?logo=postgresql&logoColor=white)

Go-бэкенд платформы Hikari Secretary. Это модульный монолит: единый владелец
бизнес-данных, авторизации Mini App, API и фоновых задач для бота.

## Текущий этап

Отмена мероприятия из Bot API и Admin API использует общий Events service:
изменение статуса, уведомления в outbox и аудит записываются атомарно.
Bot API сохраняет ответ-массив, но возвращает пустой список: уведомления
доставляет scheduler, а не обработчик callback. В аудите вызов от бота
отмечается как `bot_service`, вызов Mini App — как `telegram_admin`.

Административный API мероприятий, публикаций, медиа и отзывов реализован.
Контракт: [OpenAPI](openapi/openapi.yaml). Порядок вызовов и ограничения:
[Admin API](docs/admin-api.md).

В `v0.3.0-dev` реализованы фундамент, контур доступа и первый предметный
срез людей:

- конфигурация окружения и безопасное завершение HTTP-сервера;
- PostgreSQL в Docker Compose;
- версионируемые SQL-миграции и отдельный контейнер-мигратор;
- `GET /healthz` и `GET /readyz`;
- проверка подписи и срока действия Telegram Mini App `initData`;
- допуск в административный API только Telegram ID из конфигурации;
- синхронизация Telegram-идентичности из бота по отдельному межсервисному
  токену;
- закрытый Bot API для профиля, мероприятий, регистраций, посещаемости,
  отзывов и scheduler-операций;
- модуль Learning Content: DeepSeek, проверка JLPT и структуры ответа,
  история тем, rich message и автоматическая постановка публикаций в очередь;
- административный список людей с разрешёнными фильтрами, сортировками и
  размерами страницы `10`, `20`, `30`;
- начальный OpenAPI-контракт и закрытый `GET /api/v1/admin/me`.

Python-бот направляет в этот сервис профили, мероприятия, регистрации,
посещаемость, отзывы, напоминания, публикации и временные диалоги. Генерация,
проверка, история и планирование AI-материалов полностью принадлежат backend;
бот остаётся Telegram UI и delivery-адаптером. SQLite служит только входом
одноразового импортёра.

## Быстрый старт для разработки

Compose-файлы находятся в корне интеграционного репозитория. Из корня:

```sh
docker compose -f docker-compose.bot-local.yml up -d --build backend
```

Запускаются PostgreSQL, миграции и backend. База локального стенда должна
быть подготовлена заранее; `LOCAL_DATABASE_NAME` выбирает её имя.
API остаётся во внутренней сети Docker. Для работы через браузер запустите
miniapp тем же файлом. Отдельного Compose в backend больше нет.

## Доступ Mini App

Backend не доверяет данным, которые браузер Mini App может сформировать сам.
Клиент передаёт **исходную** строку `Telegram.WebApp.initData` в заголовке:

```http
Authorization: tma <Telegram.WebApp.initData>
```

Backend проверяет HMAC-подпись Telegram и время `auth_date`; по умолчанию
строка действительна один час. Затем он сверяет `user.id` с
`ADMIN_TELEGRAM_IDS`. Поэтому изменённые и устаревшие данные получают `401`, а
пользователь Telegram без роли администратора — `403`.

Это правило обязательно для каждого будущего endpoint с данными. Единственные
незащищённые пути — `/healthz` и `/readyz`; они не содержат пользовательских
или предметных данных.

Для запуска нужны дополнительные переменные окружения:

| Переменная | Назначение |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` | Реальный токен того же бота, который открывает Mini App. Нужен только серверу для проверки подписи. |
| `ADMIN_TELEGRAM_IDS` | Список числовых Telegram ID администраторов через запятую. Пустой список не допускается. |
| `TELEGRAM_INIT_DATA_MAX_AGE` | Допустимый возраст подписи, по умолчанию `1h`. |
| `BOT_SERVICE_TOKEN` | Отдельный длинный случайный секрет для запросов Python-бота к внутренним endpoints backend. Не равен токену Telegram-бота. |

Токен и рабочий `.env` не коммитятся. На этом этапе список ролей намеренно
хранится в конфигурации: таблицы пользователей и постоянная модель ролей будут
добавлены вместе с первым предметным API. До этого конфигурация остаётся
единственным источником прав доступа.

## Проверки и импорт

Из `backend/`:

```sh
go test ./...
TEST_DATABASE_URL="postgres://..." go test -count=1 -tags=integration ./...
go run ./cmd/import-legacy --sqlite ../data/bot.sqlite3 --json
```

Интеграционные тесты требуют PostgreSQL и создают временные схемы.
Перенос серверного SQLite выполняется production-стеком по инструкции
`docs/production.md` интеграционного репозитория. Сначала остановите старого
бота и сохраните резервную копию; одноразовый снимок и импорт сохраняют
исходные данные. После перехода новые записи хранятся только в PostgreSQL.

## Структура

```text
cmd/api/                 # HTTP API
cmd/migrate/             # применение SQL-миграций
internal/platform/       # конфигурация, PostgreSQL, мигратор и HTTP-инфраструктура
migrations/              # упорядоченные SQL-миграции
openapi/                 # версионируемый контракт API
```

## Границы

- PostgreSQL станет единственным хранилищем после переноса данных с SQLite.
- Mini App и Python-бот не будут подключаться к PostgreSQL напрямую.
- Модель постоянных ролей и доменные endpoints будут добавлены до подключения
  пользовательских интерфейсов; временный allowlist администраторов уже
  закрывает текущий API.
- API работает за reverse proxy; TLS не завершается самим Go-сервисом.
