# Административный API

Все маршруты ниже имеют префикс `/api/v1/admin` и требуют
`Authorization: tma <исходный Telegram initData>`. Автор команд берётся из
проверенной авторизации. `GET /me` возвращает данные текущего администратора.
Сервисный токен бота нельзя передавать браузеру. Форматы запросов и ответов
описаны в [OpenAPI](../openapi/openapi.yaml).

## Создание мероприятия и публикации через API

Этот сценарий предназначен для API-клиентов, которые создают сообщение сами.
Mini App настраивает существующие черновики из Telegram по схеме ниже.

1. `GET /targets` возвращает разрешённые ключи и названия из TARGETS_PATH.
2. `POST /media` принимает тело JPEG/PNG напрямую, без multipart; возвращает
   id, size и content_type. `GET /media/{id}` возвращает изображение.
3. `POST /publications`: text, media_ids, target_keys. Ответ: id черновика.
   Необязательный Idempotency-Key (до 128 символов) защищает повтор создания:
   с тем же ключом и администратором возвращается исходная публикация,
   новое тело игнорируется.
4. `PUT /publications/{id}` полностью заменяет текст, медиа и цели черновика.
   После планирования изменение запрещено. Создание/замена медиа-ссылок
   и целей выполняется в одной транзакции.
5. `POST /events`: publication_id, title, starts_at, ends_at. Привязывает
   мероприятие к черновику; повтор обновляет активное мероприятие того же
   черновика. Начало в будущем, окончание после начала, максимум 5 активных.
   Общая реализация используется также Bot API.
6. `POST /publications/{id}/schedule`: scheduled_at в RFC3339 либо пустой
   объект для немедленной публикации. Требуется хотя бы одна цель.
   Максимум 5 публикаций в очереди. Доставку выполняет существующий бот.
7. `POST /publications/{id}/cancel` отменяет черновик/ожидающую публикацию.
   Уже отправленные или находящиеся в отправке сообщения не отзываются.
   Отмена публикации не равна отмене мероприятия.

## Просмотр и отмена

- `GET /publications`: page, page_size (10/20/30), status, source, target,
  from/to (период scheduled_at), sort, order.
- `GET /publications/{id}`: содержание, media_ids, доставки и мероприятие.
  Пути файлов не раскрываются. Старые медиа бота не имеют upload id.
- `GET /events`, `GET /events/{id}`, `GET /events/{id}/participants`:
  существующие таблицы, статистика и фильтры из OpenAPI.
- `GET /events` поддерживает `search` по названию или ID мероприятия.
- `GET /people` поддерживает `search` по ФИО, отображаемому имени, Telegram
  username (с `@` или без), внутреннему ID или Telegram ID.
- `POST /events/{id}/cancel`: атомарно отменяет мероприятие и записывает
  уведомления в outbox и аудит. Повтор возвращает 409 без дублей уведомлений.
- `GET /feedback` поддерживает `search` по названию или ID мероприятия,
  ФИО, отображаемому имени, Telegram username (с `@` или без), внутреннему
  ID автора, Telegram ID автора или ID отзыва. Точные фильтры `event_id`
  и `author_id` (внутренний ID человека) можно сочетать с поиском.
  Другие параметры списка: page, page_size, kind (general/event),
  from/to (created_at), sort, order.
- `GET /feedback/{id}`: полный текст, автор и мероприятие.

Периоды включают from и исключают to; from должен быть раньше to.
Поиск в `/events`, `/event-workspace`, `/people` и `/feedback` сопоставляет буквальные
подстроки без учёта регистра, включая символы `%` и `_`.
Поле `items` в пустой странице содержит `[]`.
Основные ошибки включают `400 invalid_request`, `401 unauthorized`,
`403 forbidden`, `404 not_found`, `409 invalid_state` или `capacity_limit`
и `413 media_too_large`. У отдельных операций есть дополнительные коды.

### Сортировка списков

Сортировка применяется на сервере перед пагинацией. Параметр `order`
принимает `asc` или `desc`. При равенстве значений сохраняется
стабильный порядок по ID. В объединённом списке `/event-workspace`
при равенстве сначала учитывается тип записи, затем ID.
Для `/people` порядок по умолчанию для `name` — `asc`, для остальных полей —
`desc`. В ответе `sort.field` и `sort.order` сообщают применённую сортировку.

| Список | Допустимые значения `sort` |
| --- | --- |
| `/events`, `/event-workspace` | `id`, `title`, `starts_at`, `created_at`, `status`, `registrations`, `attended` |
| `/events/{id}/participants` | `person_id`, `name`, `telegram`, `registered_at`, `cancelled_at`, `status`, `attended`, `needs_pass`, `is_russian_citizen`, `is_itmo_student` |
| `/people` | `id`, `name`, `visits`, `last_visit`, `feedback_count`, `is_russian_citizen`, `is_itmo_student` |
| `/publications` | `id`, `text`, `status`, `created_at`, `scheduled_at` |
| `/feedback` | `id`, `text`, `event_title`, `author_name`, `created_at` |
| `/ai/history` | `id`, `title`, `scheduled_for`, `status`, `publication_status`, `attempts` |

В списке участников встречи `telegram` сортирует по username без учёта
регистра. Участники без username идут последними при обоих направлениях.
В списке публикаций при сортировке по `scheduled_at` записи без даты
идут последними при `asc` и первыми при `desc`.
В истории ИИ при сортировке по `publication_status` задания без связанного
статуса идут последними в обоих направлениях.

## Настройка черновика из бота

`PUT /api/v1/admin/publications/{id}/settings` принимает обязательный
`target_keys` (массив без повторений, только настроенные ключи) и опциональный
`event: {title, starts_at, ends_at}`. Отсутствующий/null event сохраняет
существующее мероприятие. Для отключения/отмены используются отдельные
сценарии, а не неявное удаление связей. Допускается только status=draft.
Событие и цели сохраняются атомарно, исходный текст/entities/rich_message,
фото и source не меняются. Повтор обновляет то же мероприятие.

GET публикации возвращает `media: [{position, url}]`. Изображение читается
через защищённый `GET /publications/{id}/media/{position}`. Разрешены JPEG/PNG
в ADMIN_MEDIA_DIR или BOT_MEDIA_DIR (по умолчанию `/app/data/media`), включая
проверку реального пути после разрешения symlink. Backend и бот должны видеть
один volume; наружу файловые пути не выдаются.

Постановка в очередь остаётся отдельным `POST .../schedule`. Общий с ботом
repository блокирует изменение целей во время планирования, проверяет
активность встречи и требует время публикации раньше её начала. При ошибке
планирования сохранённые настройки остаются в черновике.

Бот сохраняет файлы после отправки и отмены, чтобы история/preview работали
для обоих источников. Автоматическая очистка неиспользуемых медиа пока отсутствует.

## Загрузка через Admin API

JPEG/PNG до 10 MiB; максимум 10 файлов в публикации; сумма ширины и высоты
до 10000, отношение сторон до 20. Текст до 4096 символов без медиа,
подпись до 1024 с медиа. Клиент не задаёт файловые пути или chat_id.

ADMIN_MEDIA_DIR по умолчанию data/admin-media. Backend и бот должны видеть
этот каталог по одинаковому пути и иметь права записи/чтения соответственно.
В production Compose общий каталог смонтирован в `/app/data` обоих сервисов.
Локальный Compose для черновиков бота совместно монтирует `./data/media`
в `/app/data/media`.
Для отдельного запуска backend настройте каталог и TARGETS_PATH явно.
Загруженные файлы сохраняются для повторного использования и просмотра;
бот не удаляет медиа публикаций source=miniapp. Автоматического удаления
неиспользуемых загрузок пока нет: учитывайте этот каталог при backup/retention.

## Имена в таблице отзывов

В списке отзывов дополнительно возвращаются `author_name` (ФИО или
отображаемое имя) и nullable `event_title`. Это позволяет показать таблицу
без отдельного запроса на каждую строку; исходные ID сохраняются для ссылок.

## Настройки и история ИИ

- `GET /api/v1/admin/ai/settings`: `jlpt_level`, nullable `admin_comment`,
  `enabled` — генератор настроен при запуске backend. Секреты не возвращаются.
- `PUT /api/v1/admin/ai/settings`: уровень `N5`…`N1`, комментарий до 500
  символов или null. Неизвестные поля запрещены; `updated_by` определяется
  проверенным администратором, а не телом запроса. Настройки доступны без
  подключения провайдера и общие с ботом через learningcontent repository.
- `GET /api/v1/admin/ai/history`: `page`, `page_size`, `status`,
  `sort` (по умолчанию scheduled_for), `order` (по умолчанию desc). Возвращает
  стандартный табличный envelope и задания со статусом, попытками,
  материалом, `publication_id`, `publication_status`, последней ошибкой
  и полями `version_count` и `can_regenerate`.
  Для пустой страницы `items` — `[]`. Фильтр `status` относится к заданию.
  Сортировка по названию использует `topic.title`, как при подготовке публикации; для старых записей без названия используется `title_ru`, `theme` или `topic`.
- `GET /api/v1/admin/ai/history/{id}` возвращает объект задания в том же
  формате, что элементы списка. Некорректный ID даёт `400`, отсутствующее
  задание — `404`.
- `GET /api/v1/admin/ai/history/{id}/versions` возвращает страницы
  сохранённых материалов, включая текущий. Элемент состоит из номера
  `version` (начиная с 1) и объекта `topic`. Стандартный табличный ответ
  использует `page` и `page_size` (по умолчанию 1 и 10, допустимые размеры
  10, 20 и 30), фиксированную сортировку `version desc` и пустой объект
  `filters`. На пустой странице `items` равно `[]`. Некорректный ID или
  параметры пагинации дают `400 invalid_request`, отсутствующее задание —
  `404 not_found`.
- `GET /api/v1/admin/ai/history/latest` возвращает последнее задание
  в формате `AIJob` или `204`, если подходящих записей нет. Сервер выбирает
  запись с наибольшим `scheduled_for`, затем с наибольшим ID, и пропускает
  начальные задания в статусе `pending` без попыток, ручного запроса, темы
  и публикации. Фильтры, сортировка и страницы списка истории на выбор
  не влияют.
- `POST /api/v1/admin/ai/history/latest/regenerate` принимает запрос без тела,
  заново выбирает последнее задание и проверяет доступность его замены.
  При постановке в очередь возвращает `202` с `{"accepted": true, "id": 123}`.
  Отсутствие последнего задания или недопустимое состояние даёт
  `409 invalid_state`, отключённый генератор — `503 ai_disabled`.
- `POST /api/v1/admin/ai/history/{id}/regenerate` доступен администратору.
  Запрос без тела ставит задание в очередь и возвращает
  `202` с `{"accepted": true}`. Некорректный ID даёт `400 invalid_request`,
  отсутствующее задание — `404 not_found`, недопустимое состояние —
  `409 invalid_state`, отключённый генератор — `503 ai_disabled`.

`can_regenerate` в ответах с заданиями равно `true` при подключённом
генераторе в двух случаях. Первый — задание в статусе `failed` без связанной
публикации. Второй — задание в статусе `scheduled` или `failed` связано
с запланированной публикацией ИИ, у которой есть доставки и все они
в статусе `pending`. POST проверяет условия заново. Для просроченного
задания без публикации материал ставится
на отправку сразу после успешной генерации. У уже запланированной публикации
сохраняются ID, время отправки и цели. Содержимое заменяется только после
успешной генерации, пока доставка не началась. На ручной запрос приходится
одна попытка генерации. Если она завершается ошибкой, подробности доступны
в поле `last_error`.

`publication_status` показывает текущий статус связанной публикации
(`draft`, `scheduled`, `sent`, `failed` или `cancelled`). Если связанной
публикации нет, значение равно `null`.

Поле `version_count` в `AIJob` показывает число сохранённых версий, включая
текущую. До первого сохранённого материала значение равно 0. Новая версия
записывается при изменении сохранённого объекта `topic`.
Миграция 010 сохраняет последнюю доступную тему старого задания как версию 1.

Настройки и история используют таблицы `ai_topic_settings`, `ai_topic_jobs`
и `ai_topic_versions`.
Генератор и ключ провайдера настраиваются в окружении backend.

## Проверки API

`go test ./...` — unit-тесты.
`go test -count=1 -tags=integration ./...` с TEST_DATABASE_URL — PostgreSQL.
Admin API tests создают отдельную временную схему и применяют все миграции.
Bot API integration test также создаёт временную схему и применяет миграции;
он не зависит от состояния public и не оставляет демонстрационные мероприятия.
Используйте отдельную тестовую/локальную dev БД с правом CREATE SCHEMA.

Покрыты загрузка и проверка изображений, замена черновика, разрешённые цели,
планирование и delivery, отзывы, лимит мероприятий, общий путь Bot API,
повтор создания, повтор отмены и rollback при ошибке записи outbox.


### Единый список для страницы мероприятий

`GET /api/v1/admin/event-workspace` объединяет мероприятия и черновики
публикаций с общей серверной пагинацией, поиском по названию или ID записи
и сортировкой. Фильтр `status` принимает `draft`,
`active`, `completed`, `cancelled`. Поля `kind` и `id` различают сущности:
`draft` открывается через `publication_id`, `event` через `id` мероприятия.
Черновик можно найти и по ID публикации, и по ID связанного мероприятия.
Связанное с черновиком мероприятие не дублируется. У черновиков без
мероприятия даты равны null; фильтр периода их исключает. После постановки
анонса в очередь связанное мероприятие возвращается как `event`.

## Список мероприятий и напоминания в Bot API

Эти операции доступны боту внутри сети Docker по сервисному Bearer-токену.
Бот передаёт Telegram ID из update. Контракты запросов и ответов описаны в
[OpenAPI](../openapi/openapi.yaml).

- `GET /internal/bot/v1/events?view=upcoming&telegram_id=…` возвращает будущие
  опубликованные встречи и собственные активные записи на будущие встречи.
  Поле `registered` определяет действие в списке. Для записанного участника
  сервер также возвращает настройку напоминания.
- `PATCH /internal/bot/v1/events/{publication_id}/registrations/{telegram_id}/reminder`
  меняет настройку для активной записи до начала встречи. Положительное число
  задаёт минуты до начала, явное `null` отключает напоминание. Настройка хранится
  в той же регистрации, сохраняя время записи и данные о посещении.
- При завершении записи бот передаёт `publication_id` и `stage=reminder`
  в `DELETE /internal/bot/v1/flows/{telegram_id}/registration`. Сервер удаляет
  сохранённый диалог только при совпадении публикации и шага. При закрытии
  устаревшей анкеты бот указывает тот шаг, на котором остановился участник. Вызов без этих
  параметров завершает диалог регистрации без проверки публикации и шага.
- `GET /internal/bot/v1/reminders/due` возвращает интервал вместе с данными для
  доставки. При подтверждении отправки через `POST /internal/bot/v1/reminders/mark-sent`
  бот передаёт этот интервал, чтобы подтверждение прежней отправки учитывало
  возможное изменение настройки.
