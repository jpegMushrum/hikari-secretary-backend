# Административный API

Все маршруты ниже имеют префикс `/api/v1/admin` и требуют
`Authorization: tma <исходный Telegram initData>`. Автор команд берётся из
проверенной авторизации. Сервисный токен бота нельзя передавать браузеру.

## Создание мероприятия и публикации

1. `GET /targets` возвращает разрешённые ключи и названия из TARGETS_PATH.
2. `POST /media` принимает тело JPEG/PNG напрямую, без multipart; возвращает
   id, size и content_type. `GET /media/{id}` возвращает изображение.
3. `POST /publications`: text, media_ids, target_keys. Ответ: id черновика.
   Необязательный Idempotency-Key (до 128 символов) защищает повтор создания:
   с тем же ключом и администратором возвращается исходная публикация,
   новое тело игнорируется.
4. `PUT /publications/{id}` полностью заменяет текст, медиа и цели черновика.
   После планирования изменение запрещено. Создание/замена медиа-ссылок
   и целей выполняется в одной транзакции.
5. `POST /events`: publication_id, title, starts_at, ends_at. Привязывает
   мероприятие к черновику; повтор обновляет активное мероприятие того же
   черновика. Начало в будущем, окончание после начала, максимум 5 активных.
   Общая реализация используется также Bot API.
6. `POST /publications/{id}/schedule`: scheduled_at в RFC3339 либо пустой
   объект для немедленной публикации. Требуется хотя бы одна цель.
   Максимум 5 публикаций в очереди. Доставку выполняет существующий бот.
7. `POST /publications/{id}/cancel` отменяет черновик/ожидающую публикацию.
   Уже отправленные или находящиеся в отправке сообщения не отзываются.
   Отмена публикации не равна отмене мероприятия.

## Просмотр и отмена

- `GET /publications`: page, page_size (10/20/30), status, source, target,
  from/to (период scheduled_at), sort (created_at/scheduled_at), order.
- `GET /publications/{id}`: содержание, media_ids, доставки и мероприятие.
  Пути файлов не раскрываются. Старые медиа бота не имеют upload id.
- `GET /events`, `GET /events/{id}`, `GET /events/{id}/participants`:
  существующие таблицы, статистика и фильтры из OpenAPI.
- `POST /events/{id}/cancel`: атомарно отменяет мероприятие и записывает
  уведомления в outbox и аудит. Повтор возвращает 409 без дублей уведомлений.
- `GET /feedback`: page, page_size, event_id, author_id (ID человека),
  kind (general/event), from/to (created_at), sort=created_at, order.
- `GET /feedback/{id}`: полный текст, автор и мероприятие.

Периоды включают from и исключают to; from должен быть раньше to.
Сортировки завершаются стабильным id. Пустые списки — массивы, не null.
Основные ошибки: 400 invalid_request, 401 unauthorized, 403 forbidden,
404 not_found, 409 invalid_state/capacity_limit, 413 media_too_large.

## Медиа и deployment

JPEG/PNG до 10 MiB; максимум 10 файлов в публикации; сумма ширины и высоты
до 10000, отношение сторон до 20. Текст до 4096 символов без медиа,
подпись до 1024 с медиа. Клиент не задаёт файловые пути или chat_id.

ADMIN_MEDIA_DIR по умолчанию data/admin-media. Backend и бот должны видеть
этот каталог по одинаковому пути и иметь права записи/чтения соответственно.
Корневой Compose монтирует общий data в /app/data обоим сервисам.
Для отдельного запуска backend настройте каталог и TARGETS_PATH явно.
Загруженные файлы сохраняются для повторного использования и просмотра;
бот не удаляет медиа публикаций source=miniapp. Автоматического удаления
неиспользуемых загрузок пока нет: учитывайте этот каталог при backup/retention.

## Проверки

`go test ./...` — unit-тесты.
`go test -count=1 -tags=integration ./...` с TEST_DATABASE_URL — PostgreSQL.
Admin API tests создают отдельную временную схему и применяют все миграции.
Существующий Bot API integration test требует миграций в основной схеме
тестовой базы. Используйте отдельную тестовую БД.

Покрыты загрузка и проверка изображений, замена черновика, разрешённые цели,
планирование и delivery, отзывы, лимит мероприятий, общий путь Bot API,
повтор создания, повтор отмены и rollback при ошибке записи outbox.
