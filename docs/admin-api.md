# Административный API

Все маршруты ниже имеют префикс `/api/v1/admin` и требуют
`Authorization: tma <исходный Telegram initData>`. Автор команд берётся из
проверенной авторизации. Сервисный токен бота нельзя передавать браузеру.

## Создание мероприятия и публикации

1. `GET /targets` возвращает разрешённые ключи и названия из TARGETS_PATH.
2. `POST /media` принимает тело JPEG/PNG напрямую, без multipart; возвращает
   id, size и content_type. `GET /media/{id}` возвращает изображение.
3. `POST /publications`: text, media_ids, target_keys. Ответ: id черновика.
   Необязательный Idempotency-Key (до 128 символов) защищает повтор создания:
   с тем же ключом и администратором возвращается исходная публикация,
   новое тело игнорируется.
4. `PUT /publications/{id}` полностью заменяет текст, медиа и цели черновика.
   После планирования изменение запрещено. Создание/замена медиа-ссылок
   и целей выполняется в одной транзакции.
5. `POST /events`: publication_id, title, starts_at, ends_at. Привязывает
   мероприятие к черновику; повтор обновляет активное мероприятие того же
   черновика. Начало в будущем, окончание после начала, максимум 5 активных.
   Общая реализация используется также Bot API.
6. `POST /publications/{id}/schedule`: scheduled_at в RFC3339 либо пустой
   объект для немедленной публикации. Требуется хотя бы одна цель.
   Максимум 5 публикаций в очереди. Доставку выполняет существующий бот.
7. `POST /publications/{id}/cancel` отменяет черновик/ожидающую публикацию.
   Уже отправленные или находящиеся в отправке сообщения не отзываются.
   Отмена публикации не равна отмене мероприятия.

## Просмотр и отмена

- `GET /publications`: page, page_size (10/20/30), status, source, target,
  from/to (период scheduled_at), sort (created_at/scheduled_at), order.
- `GET /publications/{id}`: содержание, media_ids, доставки и мероприятие.
  Пути файлов не раскрываются. Старые медиа бота не имеют upload id.
- `GET /events`, `GET /events/{id}`, `GET /events/{id}/participants`:
  существующие таблицы, статистика и фильтры из OpenAPI.
- `GET /events` поддерживает `search` по названию или ID мероприятия.
- `GET /people` поддерживает `search` по ФИО, отображаемому имени, Telegram
  username (с `@` или без), внутреннему ID или Telegram ID.
- `POST /events/{id}/cancel`: атомарно отменяет мероприятие и записывает
  уведомления в outbox и аудит. Повтор возвращает 409 без дублей уведомлений.
- `GET /feedback` поддерживает `search` по названию или ID мероприятия,
  ФИО, отображаемому имени, Telegram username (с `@` или без), внутреннему
  ID автора, Telegram ID автора или ID отзыва. Точные фильтры `event_id`
  и `author_id` (внутренний ID человека) можно сочетать с поиском.
  Другие параметры списка: page, page_size, kind (general/event),
  from/to (created_at), sort=created_at, order.
- `GET /feedback/{id}`: полный текст, автор и мероприятие.

Периоды включают from и исключают to; from должен быть раньше to.
Поиск в `/events`, `/event-workspace`, `/people` и `/feedback` сопоставляет буквальные
подстроки без учёта регистра, включая символы `%` и `_`.
Сортировки завершаются стабильным id. Пустые списки — массивы, не null.
Основные ошибки: 400 invalid_request, 401 unauthorized, 403 forbidden,
404 not_found, 409 invalid_state/capacity_limit, 413 media_too_large.

## Медиа и deployment

### Настройка черновика из бота

`PUT /api/v1/admin/publications/{id}/settings` принимает обязательный
`target_keys` (массив без повторений, только настроенные ключи) и опциональный
`event: {title, starts_at, ends_at}`. Отсутствующий/null event сохраняет
существующее мероприятие. Для отключения/отмены используются отдельные
сценарии, а не неявное удаление связей. Допускается только status=draft.
Событие и цели сохраняются атомарно, исходный текст/entities/rich_message,
фото и source не меняются. Повтор обновляет то же мероприятие.

GET публикации возвращает `media: [{position, url}]`. Изображение читается
через защищённый `GET /publications/{id}/media/{position}`. Разрешены JPEG/PNG
в ADMIN_MEDIA_DIR или BOT_MEDIA_DIR (по умолчанию `/app/data/media`), включая
проверку реального пути после разрешения symlink. Backend и бот должны видеть
один volume; наружу файловые пути не выдаются.

Постановка в очередь остаётся отдельным `POST .../schedule`. Общий с ботом
repository блокирует изменение целей во время планирования, проверяет
активность встречи и требует время публикации раньше её начала. При ошибке
планирования сохранённые настройки остаются в черновике. Миграций нет.

Бот сохраняет файлы после отправки и отмены, чтобы история/preview работали
для обоих источников. Автоматическая очистка неиспользуемых медиа пока отсутствует.

### Загрузка через Admin API

JPEG/PNG до 10 MiB; максимум 10 файлов в публикации; сумма ширины и высоты
до 10000, отношение сторон до 20. Текст до 4096 символов без медиа,
подпись до 1024 с медиа. Клиент не задаёт файловые пути или chat_id.

ADMIN_MEDIA_DIR по умолчанию data/admin-media. Backend и бот должны видеть
этот каталог по одинаковому пути и иметь права записи/чтения соответственно.
Корневой Compose монтирует общий data в /app/data обоим сервисам.
Для отдельного запуска backend настройте каталог и TARGETS_PATH явно.
Загруженные файлы сохраняются для повторного использования и просмотра;
бот не удаляет медиа публикаций source=miniapp. Автоматического удаления
неиспользуемых загрузок пока нет: учитывайте этот каталог при backup/retention.

## Имена в таблице отзывов

В списке отзывов дополнительно возвращаются `author_name` (ФИО или
отображаемое имя) и nullable `event_title`. Это позволяет показать таблицу
без отдельного запроса на каждую строку; исходные ID сохраняются для ссылок.

## Настройки и история ИИ

- `GET /api/v1/admin/ai/settings`: `jlpt_level`, nullable `admin_comment`,
  `enabled` — генератор настроен при запуске backend. Секреты не возвращаются.
- `PUT /api/v1/admin/ai/settings`: уровень `N5`…`N1`, комментарий до 500
  символов или null. Неизвестные поля запрещены; `updated_by` определяется
  проверенным администратором, а не телом запроса. Настройки доступны без
  подключения провайдера и общие с ботом через learningcontent repository.
- `GET /api/v1/admin/ai/history`: `page`, `page_size`, `status`,
  `sort=scheduled_for`, `order=asc|desc` (по умолчанию desc). Возвращает
  стандартный табличный envelope и задания со статусом, попытками,
  материалом, publication_id и последней ошибкой. Пустая страница — `[]`.

Новых миграций не требуется: используются существующие ai_topic_settings
и ai_topic_jobs. Генерация и изменение ключа провайдера из miniapp пока
не входят в первую браузерную версию.

## Проверки браузерного этапа

`go test ./...` — unit-тесты.
`go test -count=1 -tags=integration ./...` с TEST_DATABASE_URL — PostgreSQL.
Admin API tests создают отдельную временную схему и применяют все миграции.
Bot API integration test также создаёт временную схему и применяет миграции;
он не зависит от состояния public и не оставляет демонстрационные мероприятия.
Используйте отдельную тестовую/локальную dev БД с правом CREATE SCHEMA.

Покрыты загрузка и проверка изображений, замена черновика, разрешённые цели,
планирование и delivery, отзывы, лимит мероприятий, общий путь Bot API,
повтор создания, повтор отмены и rollback при ошибке записи outbox.


### Единый список для страницы мероприятий

`GET /api/v1/admin/event-workspace` объединяет мероприятия и черновики
публикаций с общей серверной пагинацией, поиском по названию или ID записи и сортировкой
`starts_at`, `title`, `created_at`. Фильтр `status` принимает `draft`,
`active`, `completed`, `cancelled`. Поля `kind` и `id` различают сущности:
`draft` открывается через `publication_id`, `event` через `id` мероприятия.
Черновик можно найти и по ID публикации, и по ID связанного мероприятия.
Связанное с черновиком мероприятие не дублируется. У черновиков без
мероприятия даты равны null; фильтр периода их исключает. После постановки
анонса в очередь связанное мероприятие возвращается как `event`.
